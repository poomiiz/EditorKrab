# ตรวจรีวิว EditorKrab และแผนพัฒนาต่อ

ตรวจวันที่ 13 ตุลาคม 2026 จากรุ่น **0.29.1**, commit `21c5f81d51d481d739ae3a0ec0a698534beb495c` และ PR #95 ที่ `97936b62d621e0a499e9f00ee04dc8b01184014d` รอบนี้อ่านโค้ดและหลักฐาน ไม่มีการแก้ฟีเจอร์หรือรวม PR การทดลองกับไฟล์จริงใน E:\Movie เป็นงานอีกส่วนและยังไม่มีผลในรายงานนี้

## สิ่งที่รีวิวอธิบายถูก

EditorKrab เป็น Early Access สำหรับช่วยเตรียมร่างคลิปสั้น มีซับไทย คำพร้อมเวลา preset การเลือกเรื่องผ่าน agent การสร้างหลายร่างด้วย `--all` และระบบทีมในโค้ด รุ่น 0.29.1 เผยแพร่แล้ว โดย CI และการ Update จาก 0.29.0 ผ่านบน Windows, Mac Intel และ Apple Silicon แต่ยังไม่มีการตรวจเปิด–แก้–บันทึก–เปิดใหม่–ส่งออกใน CapCut บน Mac ของผู้ใช้

หลักฐาน: [README ของรุ่นที่ตรวจ](https://github.com/poomiiz/EditorKrab/blob/21c5f81d51d481d739ae3a0ec0a698534beb495c/README.md), [Release และผลตรวจ](https://github.com/poomiiz/EditorKrab/releases/tag/v0.29.1), [Update CI](https://github.com/poomiiz/EditorKrab/actions/runs/38389874905)

## PR #95 ใช้เป็นจุดเริ่มได้ แต่ยังไม่พร้อมรวม

[PR #95](https://github.com/poomiiz/EditorKrab/pull/95) ยังเป็น draft และ GitHub แจ้ง conflict ขณะตรวจ เพิ่ม checkpoint ของช่วงประมาณ 10 นาทีจริง แต่มีส่วนที่ต้องตรวจและแก้ก่อนรวม:

- checkpoint ผูกเพียงขนาดไฟล์กับเวลาแก้ไขแบบจำนวนเต็ม ยังไม่มีตัวระบุเนื้อหา โมเดล ภาษาและค่าถอดเสียง ผลที่ทำต่ออาจผสมหลังเปลี่ยนการตั้งค่า ส่วนการใช้ transcript สำเร็จซ้ำโดยไม่ตรวจต้นฉบับเป็นข้อจำกัดเดิมด้วย
- “ไม่เกิน 10 เรื่อง” เป็นคำสั่งใน prompt ยังไม่มีการบังคับจำนวน จัดอันดับหรือตรวจซ้ำใน backend การแบ่งเรื่องต่ออาจได้เกินสิบคลิป
- โหมด auto ยังอ่านเสียงทั้งไฟล์เพื่อตรวจภาษา และจุดเงียบไม่ได้พิสูจน์ว่าเป็นขอบคำทุกครั้ง การทดสอบใช้เสียงสังเคราะห์ 70 วินาทีและจำลอง ASR
- ตอนแก้ conflict ต้องเก็บ `timed(...)` และ trial log จาก PR98 ไว้ การอ่าน `speech_language` แก้ในรุ่นปัจจุบันแล้ว ส่วน web AI packet ตัดเวลาระดับคำออกอยู่ก่อนแล้ว

## แผนพัฒนาที่เสนอ

เริ่มเก็บผลไฟล์จริง 20/60 นาทีและไฟล์ที่ยาวที่สุดก่อน พร้อม revision, codec, โมเดล, อุปกรณ์, เวลา, peak RAM/VRAM, พื้นที่ชั่วคราวและข้อผิดพลาด แล้วใช้ผลนั้นจัดขนาดช่วงและขีดจำกัด

| ลำดับ | งานและส่วนเดิมที่ใช้ต่อ | เกณฑ์ผ่านก่อนขยับต่อ |
|---|---|---|
| 1. ถอดเสียงและทำต่อ | ต่อจาก `transcribe`/`_batched`, atomic write และ PR95; เก็บ manifest ของช่วงพร้อมตัวตนต้นฉบับและการตั้งค่า | หยุดกลางงานแล้วทำต่อเฉพาะช่วงที่ยังไม่สำเร็จ; ต้นฉบับ/โมเดล/ภาษาเปลี่ยนต้องไม่ใช้ผลเก่าปน; ตรวจคำหายและคำซ้ำที่รอยต่อด้วยเสียงจริง |
| 2. โหมดฉบับเต็ม | ใช้ timeline/source mapping และ undo เดิม; กำหนด schema รายการตัด รุ่นข้อมูลและโหมด output ให้ชัด | ตัดไฟล์ 20/60 นาที บันทึก เปิดใหม่ และแปลงเวลาซับถูกต้อง; MP4 กับร่าง CapCut ผ่านคนตรวจ; ระบุการรองรับหลายไฟล์แยกจาก renderer ปัจจุบันที่รับต้นฉบับหลักไฟล์เดียว |
| 3. เลือก Shorts | ใช้ stories และ `--all`; เก็บ candidate, เหตุผล, คะแนนและตัวระบุช่วง แล้วตรวจจำนวนและความซ้ำใน backend | ได้ไม่เกินจำนวนที่กำหนด ช่วงและเวลาใช้ได้ ประเด็นไม่ซ้ำ และคนตรวจว่าต้น–ท้ายเรื่องครบ; pilot แรกผ่านก่อนสร้างชุด |
| 4. Proxy/คิว/render ทำต่อ | ต่อจาก proxy และ JobStore; ตรวจ cache ด้วยต้นฉบับ+รายการตัด, ตรวจไฟล์ก่อนใช้, คิวบนดิสก์และผลแต่ละช่วง | ยกเลิก/รีสตาร์ตหนึ่งงานไม่กระทบงานอื่น; ทำต่อเฉพาะส่วนขาด; ตรวจ decode, ความยาว, เสียงกับภาพและรอยต่อ; ต้องไม่เขียนทับงานที่คนแก้โดยไม่เก็บคืน |
| 5. ตรวจรับงานจริง | เพิ่มเกณฑ์ทุกขั้นตั้งแต่ข้อ 1 และ protocol ฉบับเต็ม/หลาย Shorts แยกจาก pilot เดิม | ดูผลงานจริงครบ ตรวจชื่อ/ตัวเลข/ซับ/เสียง/ภาพและ CapCut roundtrip; เก็บงานล้มและ retries; รายงานเวลาคนและ elapsed แยกกัน; ใช้เปอร์เซ็นต์เมื่อมี trial ที่จับคู่ครบเท่านั้น |

ข้อ 3 ทำคู่ขนานกับข้อ 2 ได้หลังเวลาและตัวตน transcript ชัด ส่วน render ทำต่อต้องอาศัยรายการตัดและตัวตน artifact ที่คงที่ ไม่จำเป็นต้องแยกไฟล์ใหญ่ทั้งหมดก่อนเริ่ม แต่ควรแยกหน้าที่ที่เปลี่ยนร่วมกันเมื่อเพิ่มระบบจริง

ตอนนี้ยังไม่มีเปอร์เซ็นต์ประหยัดเวลาจริง การทดลองไฟล์หนึ่งตัวให้ผลเฉพาะไฟล์และเครื่องนั้น; ผลเครื่องกับการตรวจคุณภาพโดยคนต้องรายงานตามขอบเขตของตนเอง
