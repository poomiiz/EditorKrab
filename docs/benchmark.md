# วัดว่า EditorKrab ลดเวลาตัดต่อได้กี่ %

การทดลองนี้ตอบว่า เมื่อเริ่มจากไฟล์ต้นฉบับยาว 1, 5, 20 หรือ 60 นาที แล้วทำ **คลิปสั้น 1 คลิป** คนใช้เวลาเท่าไร และส่งงานเสร็จเร็วขึ้นเท่าไรเมื่อใช้ EditorKrab ช่วยทำร่าง

**ผลจริงยังเป็น UNKNOWN จนกว่าจะมีคนตัดและจับเวลาตามขั้นตอนนี้** การผ่าน smoke test หรือ CI ยืนยันการทำงานของเครื่องมือวัด แต่ยังไม่ยืนยันเปอร์เซ็นต์ที่ประหยัดได้

## งานที่เทียบ

- **manual**: คนตัดใน CapCut ตั้งแต่เริ่มทำงานกับไฟล์ดิบจนได้ MP4 ที่ผ่าน checklist
- **editorkrab**: คนเริ่มงานด้วยแอป EditorKrab (Rust) ตามหกขั้นใน [README](../README.md) แล้วแก้ผลจนได้ MP4 ที่ผ่าน checklist เดียวกัน
- ใช้ CapCut รุ่นเดียวกันและกำหนดเครื่องมือที่อนุญาตให้ตรงกัน เช่น ใช้ซับอัตโนมัติของ CapCut ได้หรือไม่ อย่าเปลี่ยนเงื่อนไขระหว่างวิธี

แอป Rust ไม่มีสคริปต์จับเวลาแบบ trial (`run_clip.py`, `bench.py` และ `timings.jsonl` ถูกลบพร้อมแอป Python เมื่อ 25 ต.ค. 2026) การวัดรอบนี้ใช้ตัวจับเวลาของคนตามหัวข้อด้านล่างเท่านั้น

กำหนด brief ก่อนเริ่มแต่ละคู่: เนื้อหาที่ต้องการ กลุ่มผู้ชม แนว hook รูปแบบภาพ/ซับ/ปก และความยาวเป้าหมายเดียวกัน ทั้งสองวิธีต้องส่ง **1 คลิป ยาว 30–60 วินาที** ความยาวผลงานที่ผ่าน QC ภายในคู่ต้องต่างกันไม่เกิน 10% หากต้นฉบับใช้ไม่ได้ตาม brief ให้เปลี่ยนก่อนเริ่มจับเวลาทั้งคู่

ผลการทดลองนี้เป็น pilot สำหรับการทำคลิปสั้นหนึ่งคลิปจากต้นฉบับแต่ละความยาว ยังใช้สรุปการทำหลายคลิปเป็นชุดหรือการตัดคลิปยาวไม่ได้

## ต้นฉบับและการสลับคนตัด

| length_group | ต้นฉบับต่อคู่ | ผลงานต่อ session |
|---|---|---|
| 1 | A และ B ยาวประมาณ 1 นาที | 1 short, 30–60 วินาที |
| 5 | A และ B ยาวประมาณ 5 นาที | 1 short, 30–60 วินาที |
| 20 | A และ B ยาวประมาณ 20 นาที | 1 short, 30–60 วินาที |
| 60 | A และ B ยาวประมาณ 60 นาที | 1 short, 30–60 วินาที |

เลือก A/B ที่ใกล้กันทั้งคนพูด รูปแบบเนื้อหา ความเร็วการพูด เสียง และความยาก แต่ละไฟล์อยู่ในช่วง ±10% ของ length_group และความยาว A/B ต่างกันไม่เกิน 10% ใช้ความยาวจริงกรอก `source_min`

ตั้งชื่อไฟล์ต้นฉบับให้ไม่ซ้ำข้ามคู่ก่อนเริ่มทดลอง เช่น `pilot-1-a.mp4` และ `pilot-5-a.mp4` ต้นฉบับตัวเดียวกันต้องใช้ชื่อเดียวกันทั้ง manual และ editorkrab แม้อยู่คนละโฟลเดอร์งาน ห้ามเปลี่ยนชื่อหลังเริ่ม trial เพื่อหลบการตรวจว่าคนตัดเห็นต้นฉบับซ้ำ

ขั้นต่ำคือ **8 ต้นฉบับ, 2 คนตัด, 16 sessions** หนึ่งคู่มี 4 แถวดังนี้:

| editor | order | video | mode |
|---|---|---|---|
| editor1 | 1 | A | manual |
| editor1 | 2 | B | editorkrab |
| editor2 | 1 | A | editorkrab |
| editor2 | 2 | B | manual |

ทั้งสี่แถวใช้ `pair_id` เดียวกัน คนหนึ่งเห็นต้นฉบับแต่ละตัวเพียงครั้งเดียว แต่ละคนทำ manual และ editorkrab อย่างละหนึ่งงาน และแต่ละต้นฉบับผ่านทั้งสองวิธีโดยคนต่างกัน `order` คือรอบ 1/2 ของคนตัดภายในคู่นั้น ให้คนสองคนเริ่มด้วย mode ต่างกัน สลับลำดับกลุ่มความยาวเพื่อลดผลจากความล้า

ให้คนฝึกใช้ทั้งสองวิธีด้วยไฟล์อื่นก่อนทดลอง ห้ามดูร่างหรือผลของอีกคนก่อนทำงานของตนเองเสร็จ หากมีคนตัดเพียงคนเดียว คู่ยังไม่ครบและยังคำนวณเปอร์เซ็นต์จาก protocol นี้ไม่ได้

## เตรียมเครื่องและแยกรอบ

1. บันทึก Git revision ของ EditorKrab (`git rev-parse HEAD`), รุ่น CapCut, CPU/RAM/GPU/VRAM, driver, โมเดลถอดเสียง และ preset/options ที่ใช้ คงรุ่นและการตั้งค่าไว้ตลอดชุดทดลอง
2. ใช้เครื่องเดียวกันหรือเครื่องที่สเปคตรงกันและบันทึกความต่าง ปิดงานหนักที่ไม่เกี่ยวข้อง เตรียม dependency และดาวน์โหลดโมเดลล่วงหน้า
3. เตรียมสำเนาต้นฉบับและโฟลเดอร์งานแยกต่อ session รอบ EditorKrab เริ่มโดยไม่มี transcript, โปรเจกต์ หรือ draft ที่สร้างจากต้นฉบับนั้นมาก่อน ตรวจว่าโฟลเดอร์ใหม่ไม่มีไฟล์ข้างต้นโดยไม่ลบงานเดิม
4. บันทึกเงื่อนไข cache ให้ชัด รอบแรกของ session ใช้ข้อมูลจากต้นฉบับใหม่ ส่วนการแก้ข้อผิดพลาดหรือทำต่อภายใน session เดิมใช้ state เดิมได้ พร้อมเก็บเวลาทุก attempt ห้ามรันซ้ำเพื่อเลือกเฉพาะเวลาที่เร็วที่สุด
5. เก็บรายการต้นฉบับและ brief ให้ระบุได้ว่า A/B คือไฟล์ใด ต้องรักษาไฟล์เดิมและบันทึก checksum ของเนื้อหาไว้กับหลักฐานหากต้องการตรวจย้อนหลัง

## จับเวลาตั้งแต่เริ่มงานจนผ่าน QC

ใช้ตัวจับเวลาสองตัวทั้งสอง mode:

| ช่อง | วิธีวัด |
|---|---|
| `human_min` | รวมเวลาที่คนลงมือทั้งหมด ตั้งแต่เปิดไฟล์/สั่งงาน ตั้งค่า เลือกเรื่อง อ่านหรือตอบ AI อัปโหลด ดาวน์โหลด แก้ซับ/ภาพ/เสียง สั่ง export และตรวจ QC หยุดนับเมื่อคนพักหรือเครื่องทำงานโดยไม่ต้องเฝ้า |
| `elapsed_min` | จับเวลาต่อเนื่องตั้งแต่เริ่ม session จน MP4 ผ่าน QC รวมเวลารอ pipeline, AI ภายนอก, ดาวน์โหลด, export และการรันซ้ำ เก็บช่วงพักไว้ในเวลารวมพร้อมหมายเหตุ จัดตารางให้มีการรบกวนและพักน้อยที่สุด |
| `fixes` | จำนวนจุดที่แก้จากร่าง EditorKrab เช่น ซับผิด 1 คำ = 1, ตัดผิด 1 จุด = 1; manual เว้นว่าง |

อย่าเริ่มจับเวลา EditorKrab ตอนเปิดร่างที่ทำเสร็จแล้ว เพราะจะขาดเวลาคนที่ใช้ก่อนหน้านั้น การช่วยจาก agent หรือ web AI ภายนอกต้องนับเวลาที่คนลงมือใน `human_min` และเวลารอใน `elapsed_min`

กำหนดเวลาหยุดทดลองหากทำงานไม่สำเร็จไว้ล่วงหน้า เช่น ถึงเพดานเวลาที่ทีมตกลงกัน เมื่อหยุดให้ลงเวลาที่ใช้จริงและเหตุผลเป็น `qc_pass=n` อย่าทิ้งแถวที่ล้มเหลว

## รหัสรอบ

`trial_id` เป็นรหัส **หนึ่ง session ของคนตัด** ไม่ซ้ำกับ session อื่น ใส่เป็นตัวอักษรอังกฤษ/ตัวเลข/จุด/ขีด/ขีดล่าง ยาว 1–80 ตัว และเริ่มด้วยตัวอักษรหรือตัวเลข ใช้ค่าเดียวกันในชีท CSV เวลาเครื่องรายขั้นตอนไม่มีให้วัดแล้ว ให้ใช้ `elapsed_min` ที่จับด้วยมือ

## Checklist คุณภาพ

ทั้งสอง mode ต้องผ่านทุกข้อ และต้องส่งผลงานครบตาม brief:

1. ซับตรงกับเสียง สะกดถูก ไม่มีคำตกหล่น
2. ไม่มีช่วงเงียบหรือพูดซ้ำเกิน 0.5 วินาที
3. หน้าคนพูดอยู่ในกรอบและ safe zone ตามแพลตฟอร์มที่ระบุใน brief
4. คำเน้นและ hook ช่วง 3 วินาทีแรกครบตาม brief
5. เสียงไม่แตกและไม่ดังเบาสลับกัน
6. ปกและชื่อคลิปพร้อมลงตาม brief
7. export เป็น MP4 สำเร็จ เปิดดูได้ครบ และยาวตาม brief

ให้ผู้ตรวจใช้ checklist เดียวกันและดู MP4 จริง ถ้าทำได้ให้ตรวจโดยไม่เห็น mode หลังคนตัดทำทุก session เสร็จแล้ว เพื่อไม่ให้การตรวจเผยเนื้อหาล่วงหน้า ข้อที่ไม่ผ่านต้องแก้และจับเวลาต่อภายใน trial เดิม หรือบันทึกผลล้มเหลว `qc_pass=n`

## กรอกชีท

ใช้ [`benchmark-sheet.csv`](benchmark-sheet.csv) หนึ่งแถวต่อหนึ่ง session มี `trial_id` ไม่ซ้ำ ทั้ง manual และ editorkrab ต้องมีรหัสนี้ 

| คอลัมน์ | ค่า |
|---|---|
| trial_id | รหัส session |
| pair_id | รหัสคู่ A/B; เหมือนกันทั้ง 4 แถว |
| video | ชื่อไฟล์ต้นฉบับรวมสกุล ไม่ซ้ำข้ามคู่ และเหมือนกันทั้งสอง mode ของต้นฉบับเดียวกัน |
| source_min | ความยาวต้นฉบับจริง หน่วยนาที |
| length_group | 1 / 5 / 20 / 60 |
| format | short |
| mode | manual / editorkrab |
| editor | รหัสคนตัด ใช้ค่าเดิมทุกแถวของคนเดียวกัน |
| order | 1 / 2 ตามลำดับที่คนตัดทำภายใน pair |
| output_count | จำนวน MP4 ที่ทำได้จริง; งานผ่านต้องเป็น 1 |
| output_min | ความยาว MP4 จริง หน่วยนาที; งานผ่านต้องเป็น 0.5–1.0 และภายในคู่ต่างกันไม่เกิน 10% |
| human_min | เวลาคนทั้งหมด; manual ต้องมากกว่า 0, editorkrab ตั้งแต่ 0 ขึ้นไป |
| elapsed_min | เวลาต่อเนื่องจริง มากกว่า 0 และไม่น้อยกว่า human_min |
| fixes | จำนวนเต็มตั้งแต่ 0 สำหรับ editorkrab; manual เว้นว่าง |
| qc_pass | y = ผ่าน, n = ล้มเหลว/หยุดก่อนผ่าน |
| notes | ข้อผิดปกติ retry, cache, ช่วงพัก, ความช่วยเหลือภายนอก และเหตุที่ไม่ผ่าน |

ใส่ตัวเลขที่มีค่าจริงและจำกัด ห้ามใช้ค่าติดลบ, NaN หรือ Infinity เก็บแถวที่ล้มเหลวพร้อมเวลาที่ใช้จริง หากยังไม่มี MP4 ให้ลง `output_count=0`, `output_min=0` และอธิบายใน notes

## อ่านผล

สคริปต์สรุป (`bench.py`) ถูกลบแล้ว คำนวณจากชีท `benchmark-sheet.csv` ด้วยตัวเอง ตรวจรูปแบบข้อมูล การจับคู่คน/ต้นฉบับ ลำดับ และผลงานให้ครบก่อนสรุป แยกตาม length_group/format ไม่ใช้เวลาเครื่องบวกกับเวลาคน

- **% เวลาคนที่ประหยัด** = 100 × (ค่าเฉลี่ย manual human − ค่าเฉลี่ย editorkrab human) ÷ ค่าเฉลี่ย manual human
- **เร็วขึ้นกี่เท่าตามเวลาคน** (`faster_x`) = ค่าเฉลี่ย manual human ÷ ค่าเฉลี่ย editorkrab human; ถ้าค่าเฉลี่ย editorkrab human เป็น 0 จะแสดง **UNKNOWN** เพราะหารด้วยศูนย์ไม่ได้
- **% เวลารวมที่ประหยัด** = 100 × (ค่าเฉลี่ย manual elapsed − ค่าเฉลี่ย editorkrab elapsed) ÷ ค่าเฉลี่ย manual elapsed
- ค่าเป็นลบหมายถึงใช้เวลามากขึ้น เวลา pipeline แสดงแยกเพื่อวิเคราะห์จุดช้า

เมื่อกลุ่มมีแถวที่ `qc_pass=n` ผลเปอร์เซ็นต์ของกลุ่มเป็น **UNKNOWN** พร้อมจำนวนและผลลัพธ์ที่บันทึกไว้ ห้ามลบงานล้มเหลวเพื่อให้เปอร์เซ็นต์ดีขึ้น หาก pair ยังไม่ครบต้องกรอกให้ครบก่อนสรุป

pilot สองคนและหนึ่งคู่ต่อความยาวให้ผลเชิงพรรณนาของคลิปและคนชุดนี้ ยังไม่ใช่การรับรองว่าเร็วขึ้นเท่ากันสำหรับผู้ใช้ทุกคน เก็บเวลาราย session ไว้ให้อ่านความต่างได้ การเพิ่มความมั่นใจต้องทดลองเพิ่มคู่ต้นฉบับและคนตัดตาม protocol เดียวกัน

## เก็บหลักฐาน

สร้าง `docs/test-logs/benchmark-<วันที่>.md` พร้อม:

1. revision/สเปคเครื่อง/รุ่น CapCut/โมเดล/preset/options และเงื่อนไข cache
2. รายการคู่ A/B ความยาวจริง brief เป้าหมาย ลำดับ session และผล QC
3. CSV ที่กรอกครบ และตารางผลที่คำนวณ
4. เวลาราย session, failures/retries/ช่วงพัก/ความช่วยเหลือภายนอก และข้อจำกัดที่ยัง UNKNOWN

เก็บไฟล์วิดีโอตามสิทธิ์และการจัดเก็บของทีม หลักฐานที่เผยแพร่ต้องยังระบุ trial และต้นฉบับได้โดยไม่เผย path ส่วนตัว
